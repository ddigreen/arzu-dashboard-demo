# ТА-МАК / ARZU — демонстрация платформы

Первая версия веб-интерфейса для ежедневной отчётности производственной компании: сотрудники вводят данные своего участка, руководитель проверяет отчёты и смотрит показатели, администратор управляет демонстрационными пользователями и настройками.

Это основа для обсуждения и дальнейшей разработки. Суммы, счета, производственные значения и планы синтетические. Имя руководителя **Ернар Отаров** задано пользователем; остальные имена демонстрационные. Рабочее название ARZU и фирменный стиль требуют подтверждения. Демонстрационная рабочая дата зафиксирована: **25 октября 2026 года**.

Демоверсия опубликована на GitHub Pages: **[открыть ARZU](https://ddigreen.github.io/arzu-dashboard-demo/)**. Исходники: [ddigreen/arzu-dashboard-demo](https://github.com/ddigreen/arzu-dashboard-demo). Для просмотра не требуется запускать сервер на Mac. Ниже также описан локальный запуск.

## Запуск

Нужен **Node.js 20 или новее** с npm. Внешних зависимостей нет, `npm install` не требуется. Выполните команды из папки проекта:

```sh
npm run build
npm start
```

На macOS также можно открыть `start.command` из папки проекта; установка библиотек не нужна.

Откройте [локальный сайт](http://127.0.0.1:4173). Сервер слушает только `127.0.0.1` и по умолчанию использует порт `4173`. Чтобы остановить сервер, нажмите `Ctrl+C` в терминале.

Произвольные периоды и сравнение в этой версии ограничены демонстрационным октябрём 2026 года.

После изменения файлов в `src/` повторите `npm run build` и обновите страницу. Сервер отдаёт готовые файлы из `dist/`.

Проверки запускаются отдельно:

```sh
npm test
npm run check
```

`npm test` запускает **53 автоматических теста** данных и бизнес-действий. Они проверяют финансовую агрегацию, пропуски, права демонстрационных ролей, исправления, дубли, восстановление данных, атомарность записи и конфликт между вкладками. `npm run check` проверяет синтаксис JavaScript; сборка дополнительно проверяет подключение ресурсов.

Браузерный QA локальной версии выполнен в Chrome на десктопе и во встроенном браузере на мобильной ширине. Проверены полный цикл отчёта, возврат, фильтры, создание сотрудника и сохранение реального вложения. Подробности и границы проверки — в [QA_REPORT.md](QA_REPORT.md). Эти ручные проверки не входят в 53 автоматических теста.

## Демонстрационные роли

Вход выполняется обычной формой **логин + пароль**. Панель выбирается автоматически по роли учётной записи; выбор из трёх ролей убран. Данные для проверки:

| Учётная запись | Логин | Демо-пароль |
| --- | --- | --- |
| Ернар Отаров, руководитель | `ernar` | `Ernar2026!` |
| Администратор | `admin` | `Admin2026!` |
| Сотрудник производства | `worker` | `Worker2026!` |
| Склад | `sklad` | `Sklad2026!` |
| Продажи | `sales` | `Sales2026!` |
| Финансы | `finance` | `Finance2026!` |

Эти пароли общедоступные и предназначены только для демонстрации. Проверка выполняется в браузере, поэтому это **не серверная авторизация и не защита опубликованного сайта**. В локальном хранилище сохраняются соли и хеши PBKDF2 SHA-256, а не открытые пароли. Владелец браузера всё равно контролирует код и локальные данные. Рабочие пароли в демо вводить нельзя.

Для смены аккаунта нажмите значок выхода внизу меню, затем введите другой логин и пароль. В админ-панели кнопка «Доступ» настраивает логин и пароль сотрудника. Пустой новый пароль сохраняет текущий; смена логина или пароля завершает прежнюю демо-сессию.

| Роль | Доступные сценарии |
| --- | --- |
| Руководитель | Обзор компании, финансы, производство, склад, реестр отчётов, подтверждение и возврат, детализация, журнал |
| Администратор | Сотрудники, назначение ролей и участков, статусы пользователей, планы и пороги, журнал, восстановление демоданных |
| Сотрудник | Ежедневная форма своего участка, черновики, отправка, исправление возвращённых отчётов, просмотр своих данных и вложений |

Для сотрудника доступны четыре исходных участка: производство, склад, продажи и финансы. Администратор не получает финансовые экраны автоматически. Ограничения демонстрируются в клиентском коде; данные браузера не защищены серверными правилами доступа.

Статус «Создан в демо» не отправляет письмо и не создаёт внешний аккаунт. Для входа демонстрационная запись должна быть активна и иметь настроенный логин/пароль. При создании сотрудника открывается настройка локального доступа.

## Работающие функции

- Отдельные интерфейсы руководителя, администратора и сотрудника; вход по логину и паролю; адаптация к телефону от 360 пикселей.
- Векторный логотип ARZU на экране входа и в меню; отдельный знак в мобильной шапке и значке вкладки. Нарисован для этой концепции, официальный брендбук не предоставлен.
- Переключаемые светлая и тёмная темы. Выбор сохраняется; переключение не перерисовывает форму и не теряет введённые значения.
- Мобильная форма с крупными числовыми полями, закреплёнными кнопками сохранения/отправки и отдельной кнопкой камеры.
- Фильтры периода и участка, поиск, сортировка и фильтрация отчётов по статусу.
- Финансовые графики с подсказками, переключением рядов, линиями, областями и столбцами; переход от дня или показателя к исходным отчётам.
- Сравнение периодов, контроль полноты отчётности, план/факт выпуска и доля брака.
- Выпуск по дням с линией демонстрационного плана; кольцевая структура внешних выплат с выделением операционных расходов без двойного счёта.
- Ежедневные формы, неполные черновики, автосохранение и явная отметка «Операций не было».
- Процесс «черновик → отправлен → подтверждён / возвращён»; обязательная причина возврата и исправления, история старых и новых значений.
- Запрет повторной отправки и незаметного изменения подтверждённого отчёта; проверки сумм, целых количеств, брака и операционных расходов.
- Прикрепление и скачивание локальных файлов, экспорт отфильтрованных отчётов в CSV.
- Локальное управление пользователями, демонстрационными планами и порогами; журнал действий и восстановление исходных данных.

## Правила финансов и показателей

Сводка использует **только подтверждённые отчёты**. Отсутствующий или непроверенный отчёт не означает ноль: пропуски графика остаются пустыми, полнота показывается отдельно. Нулевые операции можно подтвердить явной отметкой сотрудника.

Продажи, поступления денег и прибыль — разные понятия. Выручка берётся из отчётов продаж; внешние поступления и выплаты — из финансовых отчётов. **Прибыль не рассчитывается**: методику себестоимости и финансового результата ещё нужно согласовать с ответственным за финансы.

Остаток денег в демо: начальный остаток **8 400 000 ₸** плюс подтверждённые внешние поступления минус внешние выплаты до выбранной конечной даты. Внутренние переводы не включаются в эти потоки. Операционные расходы — часть внешних выплат, поэтому не могут превышать их сумму и не вычитаются повторно из остатка денег.

Остаток склада — последний подтверждённый фактический срез до конечной даты, а не сумма ежедневных остатков. При отметке «Операций не было» движение склада обнуляется, предыдущий подтверждённый остаток сохраняется. При нулевом выпуске доля брака не определена.

Долги клиентов представлены отдельными синтетическими счетами с частичной оплатой. Это фиксированный демонстрационный срез, а не полноценный учёт взаиморасчётов, связанный со всеми отчётами продаж и платежами.

План выпуска, минимальный запас и порог брака условные. Их изменение показывает возможности интерфейса и не означает согласования нормативов компании.

## Хранение и ограничения

- Отчёты, пользователи, настройки, счета и журнал сохраняются в `localStorage` под ключом `arzu.v1`.
- Файлы сохраняются отдельно в IndexedDB: база `arzu.attachments`, хранилище `files`. В отчёте остаются сведения о файле и его идентификатор.
- Демо-сессия хранится в `sessionStorage` под ключом `arzu.demo.session.v2`. Старый ключ выбора роли `arzu.demo.user` игнорируется.
- Локальные логины, соли и хеши демо-паролей: `localStorage`, ключ `arzu.demo.credentials.v1`.
- Тема: `localStorage`, ключ `arzu.theme`.
- Данные относятся к текущему браузеру, профилю и адресу сайта. Другой браузер, другой порт или очистка данных сайта создают отдельное состояние; файлы не переносятся автоматически вместе с CSV.
- При повреждённом сохранённом состоянии исходное значение сначала копируется в ключ `arzu.v1.corrupt.*`. Если резервную копию сохранить нельзя, приложение не перезаписывает повреждённый оригинал. Это механизм восстановления демо, а не полноценное резервное копирование.
- При обнаружении более свежих данных другой вкладки устаревшая запись блокируется, чтобы не затереть изменения.

**Нет серверной части, серверной базы, настоящих аккаунтов, общей работы разных компьютеров, серверной проверки прав и производственной системы резервного копирования.** Нет подключения к 1С и автоматического импорта Excel: Excel/CSV можно прикрепить как файлы, а реестр отчётов — выгрузить в CSV. Загруженный файл сам по себе не меняет показатели.

Не вводите в демо реальные конфиденциальные сведения. Обычная сборка заменяет только `dist/` и не сбрасывает данные браузера. Действие восстановления демоданных в интерфейсе предназначено для удаления локальных изменений и вложений.

## Что согласовано, что предложено и что уточнить

**Подтверждено запросом:** сайт с отдельными панелями руководителя, администратора и сотрудников; ежедневный ввод по ответственному участку; качественный интерфейс, интерактивные графики, возможность дальнейшей доработки. В исходном контексте также зафиксирован отказ от зелёной палитры.

**Предложения, показанные в демо:** четыре участка, конкретные формы и KPI, проверка отчётов руководителем, матрица ролей, справочник демонстрационных счетов, планы, пороги, состав уведомлений и схема локального хранения. Они помогают обсуждению, но не заменяют утверждённое техническое задание.

**Открытые вопросы:**

1. Какие 5–10 показателей нужны руководителю, и кто отвечает за каждый источник?
2. Какие подразделения, продукция, склады, единицы измерения и поля форм используются на практике? Нужны день, смена, заказ или отдельная операция?
3. Как считаются себестоимость, незавершённое производство, брак, возвраты, частичные оплаты и финансовый результат?
4. Кто проверяет данные, разрешает корректировки и закрывает периоды?
5. Какие Excel и 1С есть у компании, и какие примеры выгрузок доступны?
6. Сколько пользователей будет работать, где размещать данные и какие требования к авторизации, резервным копиям, поддержке и приёмке?

## Структура для разработчика

```text
src/
  assets/          SVG-логотип ARZU и отдельный знак
  index.html       точка входа
  theme.js         переключение и сохранение темы до отрисовки страницы
  data.js          синтетические данные, диапазоны дат и агрегация
  store.js         локальное хранение, валидация и бизнес-действия
  auth.js          локальные демо-логины, хеши паролей и сессии
  charts.js        чистые функции интерактивных SVG-графиков
  app.js           интерфейс, формы, CSV и работа с IndexedDB
  styles.css       стили и адаптивная верстка
scripts/
  build.mjs        проверка, сборка и версионирование ресурсов для браузерного кеша
  serve.mjs        локальный HTTP-сервер
tests/
  data.test.cjs    проверки исходных данных и расчётов
  store.test.cjs   проверки состояния, прав, валидации и сохранения
  auth.test.cjs    пароли, сессии и управление локальным доступом
  charts.test.cjs  разрывы данных и согласованность графиков
  theme.test.cjs   тема, сохранение выбора, недоступное хранилище
dist/              результат npm run build; вручную не редактировать
```

Модули без внешних библиотек подключаются в порядке `theme.js` (в head), затем `data.js → store.js → auth.js → charts.js → app.js`. Данные доступны через `window.ARZUData`, действия — через `window.ARZUStore`. `store.get()` возвращает независимый снимок; изменять отчёты нужно методами хранилища, чтобы сохранить проверки и историю. Эта клиентская архитектура предназначена для демонстрации: при разработке рабочей версии проверку прав, запись операций и аудит нужно перенести на сервер.
